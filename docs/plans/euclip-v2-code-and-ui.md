# Euclip v2: how code and UI work together

Status: model agreed with the project owner on 2026-11-13. Nothing is built yet.
Audience: the project owner, and whoever implements Euclip v2.
This is the design doc that section 6 of [cracked-up-and-euclip-v2.md](cracked-up-and-euclip-v2.md) promised. Where the two differ, this one is authoritative.

## 1. The model in one paragraph

**Structure lives in code; values live in the project document.** A script creates nodes, chains and sequences. Running it tells Euclip what exists, and Euclip draws a control for every parameter and a step grid for every sequence. Moving a control or editing a grid changes the document and the live sound, and never rewrites the code. The default project is ordinary generated code, so everything it does can be read and changed.

Arbitrary two-way editing between code and UI was considered and rejected: a loop or a computed value has no UI edit that maps back to text. The earlier plan (chains stored as data, with the script as a generated text view) is dropped for the same reason.

## 2. Requirements

| # | Requirement |
|---|---|
| R1 | **The script is the only definition of structure.** Nodes, chains, sequences and their callbacks exist because code created them. Sequencer construction is in the script, not hidden as it was in v1 |
| R2 | **Values are data.** Control values, step patterns, per-step lanes, slider modes and MIDI bindings are stored in the document, keyed by scope, node id and parameter name |
| R3 | **The UI is declared.** A control exists where the script declares one (section 3); grids come from named sequences. Declarations are plain data, so the same script works sandboxed and cannot inject markup |
| R4 | **UI edits never rewrite code**, with the two exceptions in R7 and section 5 |
| R5 | **Re-running never loses state.** A code edit rebuilds that script only: untouched nodes keep sounding, sequences keep phase, document values are reapplied, and a failed run leaves the previous version playing. This is cracked-up's `build` |
| R6 | **Identity is stable** (section 5) |
| R7 | **Non-coders never need the editor.** Structural actions (add a track, add an effect, add a sequence) are code edits Euclip makes from templates. Where a script is in a shape Euclip cannot locate the edit in, the action is disabled and says why |
| R8 | **Precedence is fixed and visible:** document value, then per-step lane, then what a sequence callback does for that event, then audio-rate modulators. A control shows its base value and its effective value |

## 3. Controls are declared in the code

Decided 2026-11-13. It replaces two earlier designs: "last touched wins" between a number in the code and an automatically made slider, and control markers written inside a node's options (which needed the library to treat those parameters specially). Where sections below still speak of overrides, this section wins.

A control exists only because the script declares one, on its own line, bound to a node by selector. Nodes are built as they always are.

```js
__()
  .sampler({ id: 'kick', buffer: 'kick' })
  .lowpass({ id: 'filter', frequency: 2000, q: 6 })
  .gain({ id: 'level', gain: 0.8 })
  .to('channel');

slider('#filter', 'frequency');
knob('#level', 'gain', { label: 'Level' });
```

- **`slider`, `knob` and `toggle`** are functions Euclip puts in scope: a selector, a parameter name, and optional plain-data options (label, slider mode, range overrides). More kinds may follow. cracked-up knows nothing about them.
- **Moving a control** calls `set` on the selected nodes and stores the value in the document. The script does not re-run and no node is rebuilt.
- **When the script re-runs,** the declaration line does the same `set` with the stored value, so the value passes through the script as an ordinary `set` and the rebuild ends on it by the library's normal rules.
- **The number in the node is the default:** it applies when nothing is stored, and it is what "reset" returns to. A parameter with no control is fixed by the code.
- **Range, unit and curve** come from the parameter metadata of the node the selector finds.
- **Identity** is the selector plus the parameter name. A selector may match several nodes (`slider('.voice', 'detune')`), which gives one control for all of them. A selector that matches nothing is shown as a warning on that line.
- **`controls()`** with no arguments is the one "create all the UI" call: a control for every parameter of every node the script has made so far (a section per node), a waveform editor for every sampler, and a step grid for every named sequence of the script (grids are added when the script has run to its end, so the sequence may come after the call). An explicit `slider`, `stepGrid` or `waveform` for the same thing, before or after, is used instead, with no duplicate. **`controls('#kick')`** is narrower: the parameters of those nodes and nothing else; `controls('#kick', ['speed', 'start'])` for those named.
- **A control with no node:** `const density = slider('density', { min: 0, max: 1 })`, read as `density.value`.
- **Changing a value from code** can be done two ways:
  - `__('#filter').set({ frequency: 900 })` moves the parameter and not the control. The control shows that the parameter is away from its value (R8).
  - A declaration returns the control: `const cutoff = slider('#filter', 'frequency'); cutoff.set(900)` moves the control and the parameter together, as if the user had moved it. Inside a sequence callback the change lands on the step, like any other `set`, and the control is redrawn at that moment. Changes made this way are stored but are not undo steps.
- **In the sandbox** nothing differs: the `set` is an ordinary command and the declaration is plain data sent to the host.
- **In the UI,** a node lists its declared controls. "Add control" lists the node's other parameters and writes the declaration line into the code; "remove control" deletes the line. These are code edits of the same kind as R7.
- **A sampler's speed can be synced to a sequence:** the unit `sequence-sync` ("Sequence sync" in the control's menu, with one item per named sequence of the track's own script when there are several). In it the control holds a multiplier, not a speed: 1/4, 1/3, 1/2, 1, 3/2, 2, 3 or 4 passes of the whole sound per pass of the sequence (shown as `1/2× seq`), and the speed is `multiplier × sound length ÷ sequence length`, worked out by the runner from the library's own timing of the sequence's options and applied again on every build and whenever the tempo, the sequence, the sound or the unit changes, with no document write and no undo step. The choice is stored with the control's other unit choice (`options: { mode: 'sequence-sync', sequence: 'slices' }`); in a script, `slider('#sampler', 'speed', { mode: 'sequence-sync', sequence: 'slices' })`, and without `sequence` the script's first named sequence. With no such sequence, or no sound yet, the speed is 1 and the control says it has nothing to sync to; the stored choice is kept and recovers. Changing unit into or out of it keeps the speed as near as the multipliers allow (one undo step). Nothing switches to it implicitly; the sliced-loop template declares it.
- **A sampler's region and loop points change roles when crossed:** start taken past end (or end past start; likewise the loop's two points) does not stop: it becomes the other end, so start is always the lower and end the higher, both written in the gesture's one undo step, never nearer than 1 ms. The same by dragging a handle, dragging or stepping a value box, the keys on a handle, and typing.
- **Every slider, knob and toggle on a parameter has a lane** (v1's multislider; redesigned 2026-11-21, replacing the "Single value / Per step" mode). The lane always exists; it is empty until a step is given a value of its own, Elektron-style: a **lock**. A step with no lock follows the control's single value, so the control never stops working: moving it moves every step that has no lock, and the locks stay (the owner's choice for now; it may change). Stored with the control's options as a sparse list, `options.stepValues: (number | boolean | null)[]`, in the parameter's own terms (a toggle's true or false), null for a step that follows; absent when no step has a lock (Clear all steps removes it). The lane follows the first sequence with a step grid, or another chosen in the lane's menu (`options.perStep`, the sequence's name) or written in code: `slider('#filter', 'frequency', { perStep: 'steps' })` only chooses the sequence (`true`: the first). An earlier version's `perStep: false` holds no locks until a step is next set. Length follows the sequence; locks past its end are kept in the document for when it grows. Unit, range, mode and glide carry over: a frequency in notes is a melody lane, a glide is portamento, and a synced speed's locks are multipliers (sync and lanes work together; changing the unit converts only the locked steps). Select menus have no lane. A step listener per sequence that has a lane **in play** (some lock) sets each such control's parameter to the step's value (its lock, else the single value) at the step's time, before the sequence's own callback, on every step including rests; it does parameter sets only, and an error in it is the app's, not the script's. Stopped, the parameter holds the step last played (the first, if none). A move of the control while the step now playing (or held) has a lock does not move the parameter; when a lane goes out of play the parameter returns to the single value. A script's `control.set(v)` moves the parameter until the next step and does not rewrite the lane; `.value` reads the current step's value. If the chosen sequence is not in the script, the control is at its single value and says so if it has locks.
- **Where a lane is drawn.** Under its sequence's grid, a bar per step in the step's own column (items of the step grid). A locked step is a filled bar; a step that follows is a ghost (an outline at the control's height), so moving the control moves the ghosts. A toggle's lane is a row of cells: a press on a step that follows locks it to the other value, a press on a locked step makes it follow again. Bars are dragged like sliders (across to paint, Shift for one bar finely, double click or long press for a number box in the control's unit; an empty box, Delete or Backspace make the step follow again), one undo step per gesture, the playing step marked. **Never in the track's row** (2026-11-21: the row draws its steps only, with no Lanes menu). A processor's lane is shown by one per-track choice (`laneView` in view storage, no undo: `open` and `closed` keys over a default where a lane is shown while it has locks) **under the control's own row** (its lane button, the v1 multislider icon, is pressed while the lane is open and blue while steps hold locks (its label says how many; no count is drawn); the row then spans the list's width). **Never in the steps tab** (2026-11-22: the sequence pane's grids are steps, generators and shape only; a lane is drawn with its control). **A source's lanes are shown one at a time over its editor** (`sourceLane`, view state, not remembered): a source editor has a **lane switch**: two square buttons, its picture (the waveform; a synth's keyboard, at the start of the octave bar) and its steps (2026-11-22: first a button in every cell, which made the names unreadable, then one tall toggle). The waveform's stand one over the other at the left of its values. The steps button shows the lane of the value last touched (a press or focus on a waveform cell (speed, start, end, loop start, loop end, Loop, Reverse) or on a row of the source's controls; untouched, the waveform's speed or the synth's pitch, else the source's first lane) **in the picture's place**, at its size (scrolled within where its bars want more room; a short keyboard grows to make room), so the values stay in reach and typing one moves the ghost bars of the steps that follow it; while it is open, touching another value shows that value's lane instead, and a waveform value whose lane it is has a line round it. The steps button is blue while any of the source's controls has steps of its own. The source's control rows have no lane buttons. The lane's name is a **menu of the source's lanes** (a dot marks those with steps set), and an **×** (or Escape, or the picture button) closes it; the steps button opens the lane last shown. Presses and wheel turns in it are its own (no handle moves, no zoom). A synth with no keyboard has one lane button over its lane, under its controls. The speed's menu has Show/Hide steps for the speed's lane. The loop's points (their handles and values) can be moved while the loop is off, drawn faint (2026-11-22). Loop and Reverse's names take one width, so their switches line up. The editor's values show at most three decimals (0.0871 s reads 0.087 s), the whole value on hover; a field left as it opened keeps the value whole. A lane's tools stand in a last column of its grid, to the right of its bars and at the grid's right end: its menu (the control's units and glide; **Reset**, which here puts the control and every step back to the script's default, one step to undo; Show in script; plus, where the track has several grids, the sequence it follows, then Clear all steps and Hide lane) and a small **Clear all** button, there while a step holds a value of its own (its room is kept while it is not). Each step and bar names its column (sixteen to a row) so the tools column takes nothing from the steps. The synth editor says when steps of its pitch are locked (the keys set the others); the sampler editor's cells show their values; their lane buttons turn blue when steps are locked.
- **No step picker** (removed 2026-11-21): an earlier version had one over the sound pane (choose a step, then the controls set that step's lock, with tinted rows and a step chip). The owner found it unclear and unneeded: a step's own value is set in the control's lane (its multislider) alone.
- **Step grids are sixteen to a row, everywhere** (the track list, the sequence pane, a phone): a longer sequence wraps onto further rows of sixteen, a shorter one is part of a row, and a step is one width for every grid in a view (a sixteenth of the room, up to a maximum), so step N lines up across tracks and a lane's bar stands under its step. A step keeps its height when it is narrow (about 20 px wide on a phone, still a finger tall).
- **A grid has a Length dial and a Step menu** in its header in the sequence pane. The script's `steps: 16` and `step: '1/16'` are the defaults; what is set on the grid is stored with its options (`options.length`, 1 to 64, and `options.step`, a duration as the library writes one: 1/2, 1/4, 1/4t, 1/8d, 1/8, 1/8t, 1/16d, 1/16, 1/16t, 1/32) and applied to the sequence when the script runs and at once when changed (`sequence.update`, keeping phase), one undo step per change. The pattern is kept as far as it goes and new steps are rests; the stored pattern is not cut when the length is shortened, so lengthening brings its steps back (until the pattern is next edited). A generator's dials make the pattern again for a new length when no step has been changed by hand since. Reset on the grid returns pattern, length and step length to the script's together; where they differ from the script's the header says what the script says. A sequence made with `span` can have its length changed; its step length is the span's. Everything that follows a sequence follows: a synced speed, per-step lanes, the play cursor, the track row's grid.
- **Pattern generators are part of the step grid** (the sequence pane's grids; a track row's compact grid is steps only, and its menu's "Pattern generators" leads there). Nothing is written in a script for them. The grid's stored pattern stays the only truth: a generator is a tool that writes into it, and no recipe is stored that the sequence is computed from. Behind **Generate** are four tabs of dials, all made with cracked-up's own helpers: Euclidean (`euclid`: hits, rotate), Binary (`binaryPattern`: a number up to 127, whose digits repeat to fill the grid), On / off (`onOffPattern`, repeated to fill and cut at the end) and Sieve (`sieve`: "every N from K", twice). A dial rewrites the pattern as it moves (one undo step per drag, typed value or key step). The dials of the generator last used are kept with the grid's stored options (`options.generator`, with the pattern they made), so the panel reopens where it was; steps changed by hand since are marked "edited" and are not overwritten until a dial moves again. The step count is the script's: generators fill it and never change it, so the helpers that change a pattern's length (stretch, spread, repeat, palindrome, interleave) are not offered. A generated hit keeps the value its step had (a slice number), else is 1. "Onto what is there" chooses Replace, Or, And or Xor (the library's `or`, `and`, `xor`) against the pattern as it was when the dials began. The tools ◀ ▶ Reverse Invert (`rotate`, `reverse`, `invert`) act on the pattern as it stands, one undo step each. A summary says how many steps are on and writes the pattern out (`patternToString`).
- **The waveform editor's values are three groups, left to right:** the speed; the four places in the sound (start, end, loop start, loop end) headed by the unit they share; the two switches (loop, reverse). Each is a named group, with a line between. The loop's points stay faint and disabled while Loop is off; where the places are two rows the second is captioned "Loop points". Two rows is the usual layout (the speed's cell is the height of both, the switches one over the other); one row only in an editor of 90rem or more, where every name and its longest value fit. A name is never cut short: a cell that is not wide has a shorter whole name of its own. Narrow: the speed beside the places, the switches a row beneath. The speed's cell has the same unit menu its control has in the controls pane (one control, one stored choice, two views); on a phone it is in the expanded editor. Nothing changes size or place on interaction.
- **Snap** is a label and a menu of fixed width: Zero crossing, Slices, None. Untouched, it follows the sound (Slices when it has some, else Zero crossing); a choice the person makes is kept for that waveform with the rest of how things are looked at (local storage, no undo step), and no longer follows. It applies to handle drags, value-box drags and added boundaries; typed values and key steps are exact.
- **Sounds: three places, one way round.** The **Library** is everything Euclip offers, on the server; browsing and hearing change nothing. **My sounds** are files the person added, kept across their projects (in this browser's IndexedDB for now, behind a storage interface a server with accounts would replace): a second source beside the library, not a later stage. **This project** (the pool, `samples` in the document) is the named sounds this project's scripts can refer to; each entry points at a library file (`library: path`), a built-in (`url`) or one of the person's files (`file: id`), and owns its slices. A track is not a list: each sampler plays one project sound, and usage shows as "used by Track 3". The flow is Library or My sounds → Project → a sampler, with two verbs: **Hear** (one sound at a time, no transport, the app's output, nothing changed) and **Use** (into the project if it is not there, and given to the sampler the browser names), plus **+** to add without giving. The sidebar has those three tabs.
  - *Names.* A sound that joins gets a name a script can type, made from the file's name (lower case, `a-z0-9_`, starting with a letter, at most 32 characters). The same source joining again reuses its entry; another source with the same name gets a suffix (`kick_2`). Renaming never edits a script silently: where scripts name the sound the only action is "Rename and update N scripts", one undo step; samplers that have it by the person's choice follow in any case. Duplicate makes a second name on the same source with slices of its own.
  - *A sampler's sound follows the steps rule.* `sampler({ id: 'sampler' })` with no `buffer` means the project holds the choice (the picker, or Use); a written `buffer: 'kick'` is the default and a stored choice wins. With neither, the sampler is silent and the source pane says no sound is chosen, with a way to choose. The templates write no `buffer:` and store the choice, as they store their patterns.
  - *States.* Every row and the picker say: loading, ready, failed (with Retry), missing file (one of the person's files that is not in this browser, with Supply file). Library audio is fetched only when heard or used, decoded once and shared.
  - *The library client* is one module (`app/library/`), reading the v1 API (`/v1/files/{path}`, `/v1/files/search?q=&page=`) through a base URL in the app's config; a `/v2` would replace only that.
- **Smoothing and glide are two things.** *Smoothing*: every move of a control on a continuous audio parameter (a channel strip's level and pan, a bus level, a declared slider or knob) is sent to the library as `set(value, { glide: 0.02 })`, 20 ms from wherever the parameter has got to, so a moving fader has no steps in it. It is always on, never shown and not configurable. What should jump is set at once: toggles, selects, stepped units (stepped, notes, semitones, slices, a synced speed), a sampler's places in its sound, values applied by a build, a synced speed retuned by a tempo change. The library decides per parameter what can be swept (audio-rate numbers); the app keeps no list. Undo and redo of a strip's level or pan are smoothed too; a declared control's undo is a rebuild and lands at once. *Glide*: a time the person chooses, a secondary attribute of each slider and knob on a parameter that can glide: `slider('#filter', 'frequency', { glide: 0.3 })` (seconds; the script's number is the default), or a "Glide" entry in the control's menu that opens a time box (0 to 5 s on a cubic travel, ms below a second), stored with the control's unit choice (`options.glide`), one undo step per change, with its own "Reset glide". When it is above 0 it takes the place of the smoothing for that control, wherever the control moves its parameter (drag, keys, typed value, value box, and a script's `control.set`, which then starts on its step and sweeps). The option also takes a control of the script's own, read at every move (`const glide = slider('glide', { min: 0, max: 2 }); slider('#filter', 'frequency', { glide })`); the menu then says which control it follows. On something that cannot glide (a control-rate parameter such as a sampler's speed, a stepped unit, a control with no parameter) the option is a warning on its line and the menu's Glide entry is there but disabled, with the reason beside it, so every number control's menu has the same shape. A frequency in note mode still glides (the parameter sweeps from note to note). **`min` and `max`** in a control's options set its range, narrower or wider than the parameter's own (the library's range is what a control covers, not a limit): `slider('#filter', 'q', { max: 100 })` gives a control that goes to 100, and the value reaches the node. What cannot be kept is a warning on the line and the control falls back to the parameter's range: a value that is not a finite number, a `min` not below the `max`, a `min` of 0 or less on a log-scale parameter (a frequency; the parameter's own minimum is used). A value beyond what the browser's own AudioParam accepts (`minValue`/`maxValue`, read off the library's parameter: a filter's frequency stops at the Nyquist, a compressor's ratio at 20) is held at that limit with "q cannot exceed N on this node". A stored value outside a later-narrowed range is shown and sounded at the nearest end and is not rewritten in the project until the person moves the control. A synced speed holds a multiplier, and so do its lane's locks (sync and a lane work together). The control on screen is where it was put at once; nothing animates along the glide. The channel strip has smoothing only.
- **A step is on or off** (2026-11-22). Pressing a step switches it (one undo step); a step switched on is 1. There is no value box on a step (no double click, long press or digit), and no notes mode. What a step plays beyond whether it plays is set in the lanes of the controls it drives: a synth's pitch (its `frequency` parameter), a sampler's slice (its `slice` parameter: 1 is the first slice, 0 the whole region; one of the waveform editor's own parameters, so its lane is in the waveform's lane menu). A pattern stored with larger values (an older project) still plays them, as `ev.value`, and shows them as on. Generators write 1.
- **Step grids are declared too:** `stepGrid('steps')`, placed after the `__.transport.sequence('steps', …)` call it belongs to, gives that sequence a grid. **The grid can be the only source of a pattern:** a sequence made with a count, `{ steps: 16 }`, and given a grid (by `stepGrid` or `controls()`) has no pattern in its script; the grid owns it, starts empty (all rests are applied during the build; nothing is written to the document until a step is set), and a changed count keeps the stored steps as far as they go and adds rests. The rule is exact, read from the library's `sequence.options.steps` being a number. A sequence made with an array or pattern string is as before: those steps are the default (an explicit all-ones array shows every step on) and a pattern edited in the grid is stored in the document and applied by the `stepGrid` line when the script runs. A count with no grid is untouched and fires every step. The templates and the default project use the count form, with their starting patterns in each track's stored values. A sequence with no `stepGrid` line (and no `controls()`) has no grid. (The function was first called `sequencer`; it was renamed because that read too much like `transport.sequence`. Stored scripts are migrated on load and the old name is not an alias.)
- **`waveform('#sampler')`** declares a waveform editor for a sampler, shown in the footer's source pane: a view over the sampler's ordinary controls (start, end, loop points, loop, reverse, speed) and the sound it plays. A script with several `waveform` lines gets one editor at a time, chosen from a list of them.

## 4. Scripts and where things live

One script per track, plus one project script. There is no init/onstep split: a track's script holds its chain, its sequences and their callbacks, and any modulation, in that conventional order. A track script is one cracked-up scope, which is the unit of rebuilding, error isolation and sandboxing.

Whether something belongs in a script is decided by one question: would someone change it to make different music?

| Lives in | What | How the user sees it |
|---|---|---|
| Track script | The track's chain, sequences, callbacks, modulation | Its editor |
| Project script | Buses, the master chain, shared macros, project-wide sequences or modulation | Its editor. The default is a few lines |
| Document settings | Tempo, the sample pool, MIDI bindings, snapshots, control values and modes | Panels: the sidebar pool, the footer transport, a MIDI panel. Scripts refer to them by name (`buffer: 'kick'`) |
| Provided by Euclip to every script | The names in scope (`__`, `track`, `midi`, helpers), each track's scope and output wiring, running and rebuilding | Read-only: hover docs and Cmd-click open the real source in the editor's source panel; the inspector shows the resulting graph |

The last row is the only "magic". The rule for it: host plumbing only, and readable in full. A script cannot replace it, but can do anything inside it, including ignoring the default output.

Navigation between the pieces: a control or grid can jump to the line that created it, and a read-only view can show every script of the project in order.

### Code runs as it is typed

There is no Run button and no draft. A change to a script is submitted automatically after a short pause in typing, as in the cracked-up demo.

- The text in the editor is the script in the document. There is one copy, and undo is how a change is taken back.
- If the new text has a syntax error, or throws while building, the previous version keeps running and the error is shown beside the script until it is cleared. The version still running is held in memory only.
- A project opened with a script that has an error therefore has nothing to run for that track: the track is silent and marked until the script is fixed.
- An error thrown later, inside a sequence callback, disables that callback and is shown the same way; the rest of the track and project carry on.
- Text that is valid part-way through typing does run (a number half typed, for example). The pause before submitting is the guard against that.
- A script that never returns (an endless loop) would freeze the page when run directly. The run needs a guard for this; in the sandbox the runner can simply be stopped and restarted.

The editors are `cracked-up/editor` instances sharing one catalog. Direct execution is used for a user's own project and the sandbox (`cracked-up/remote`) in collaboration mode; the script text is the same in both.

## 5. Identity

A control's configuration follows the node's identity, not its place in the chain.

- **A node with an id** keeps its configuration wherever it moves. Generated code always includes ids.
- **A node without an id** is identified by type and creation order ("the first lowpass in this track"), which is how cracked-up matches un-id'd nodes on a rebuild. Inserting a different node type does not disturb it. Adding or removing an earlier node of the same type does.
- **Automatic ids.** The first time the user configures a control on a node with no id (sets a slider mode, learns MIDI, or moves the control), Euclip adds an id to the code: `.lowpass()` becomes `.lowpass({ id: 'lowpass' })`. This is a visible code edit of the same kind as R7.
- If the script is in a shape Euclip cannot edit, the control works by position and is marked as such.
- Configuration whose node disappears from the code is kept dormant, so undoing the code edit restores it.

## 6. Slider modes

A mode maps slider position to parameter value. The user chooses it by right-clicking the control.

- Modes to start with: linear, exponential, MIDI note (the slider moves in note numbers, converted to Hz), decibels for gains, and stepped (whole numbers or a list of values).
- The stored value stays in the parameter's own unit, so switching mode changes how the slider travels and what it displays, not the sound.
- The default mode comes from the node's metadata. A script may suggest one (R3); the user's choice overrides it and can be reset.
- A lane uses the same mapping as its control.

## 7. MIDI learn

Right-click a control, choose Learn, move a knob. The document stores a binding from that channel and controller to the parameter.

- The knob goes through the control's slider mode.
- A knob move is a slider move: it sets the document value under the rule in section 3.
- The parameter jumps to the knob's position; there is no soft takeover.
- Bindings are listed in the MIDI panel, where they can be changed or removed.
- The project stores channel and controller. The port is chosen per machine, so a shared project works with each person's own controller.
- A script can also bind MIDI itself with `midi.bind`. Those appear in the same panel, marked as made by the script and read-only.

## 8. What this needs from cracked-up

Already there: `build` reconciliation, parameter metadata, named sequences with `update`, `midi.learn` and `midi.bind`, `midi.session`, the editor and its catalog, the inspector, the sandbox.

Likely additions, to confirm when implementation starts:

- A shared set of named curves, so a slider, a lane and a MIDI binding use one mapping.

## 9. The v2 app

Decided by the project owner on 2026-11-13:

- **Same monorepo** (Rails and Ember), unless a strong reason appears.
- **A new node module of its own in the monorepo**, beside `client/`, with its own `package.json`, dependencies and build. It shares no code or build with the current app, which keeps running unchanged for comparison.
- **Ember stays.** Svelte 5 was considered and judged a slightly better technical fit, but not by enough to outweigh familiarity. The document store is plain classes with reactive fields and would look much the same in either.
- **Built from scratch on current Ember practice:** TypeScript throughout, Glimmer components in template-tag files, Vite. No Ember Data.
- **Same look and feel.** The sidebar for browsing and choosing audio files, the track list and the footer are carried over, rebuilt on CSS grid.

- **The module is `client-v2/`.**
- **No backend at first.** Projects are saved in the browser (IndexedDB). Rails is wired in later under a `/v2` API namespace.
- **cracked-up is a local link** (`../../cracked-up`) while both change quickly, and becomes a pinned release once the app's needs from the library settle.
- **No NexusUI.** v2 builds its own controls (slider, multislider, step grid, toggle, dial if needed) as Glimmer components on pointer events, so they can carry slider modes (section 6), show base and effective values (R8), open the control menu, and work by touch. Icons and the logo are copied from the old app as needed.
- **Every UI decision must work on phones and tablets as well as desktop.** In practice:
  - Layouts are designed at phone, tablet and desktop widths from the start, not adapted afterwards.
  - Nothing is reachable only by hover or right-click. A right-click menu (slider modes, MIDI learn) is also opened by a long press or a visible button.
  - Touch targets are at least 44 px, and controls work with pointer events, not mouse events.
  - The code editors must be usable with an on-screen keyboard, and the app must be fully usable without opening one (R7).

- **Layout follows v1:** transport in the project bar at the top; the footer is the selected track's detail, and becomes a bottom sheet on small screens.
- **Poppins is shipped with the app** (self-hosted).
- **Hints are behind a "?".** Nothing in the app explains itself by default. An interface that has something to say about how it works (the waveform editor, the controls, step grid and source panes, the channel strip, the sound browser) has a small "?" button that opens a popover with the hints; it opens on a click or a tap (never on hover alone), and closes on a second one, on Escape, or on a press elsewhere. It is one shared component (`ui/hint`), built in the app, and every interface uses it rather than writing help into its layout. What is going on now is not a hint and stays where it applies: errors and warnings, a count or a value, a label, a control being out of step with its parameter, "this script declares no controls".
- **Deferred, by decision:**
  - Drag handles to resize most containers (wanted eventually; the grid areas should be sized by custom properties so handles can be added).
  - A limited UI for very small screens (around 320 px), to be planned separately. Until then, layouts are simply as responsive as they can be.
  - Scopes, visualisations and metering, which will be rethought rather than ported from v1.

### The signal chain in the track row

*Signal levels.* While a chain is on screen its links and end chips show the real level: a tap (an analyser off a node's output, never in the signal path) on each visible node, read with the inspector's own `TapSet`, `measure` and `LevelMeter`/`RangeMeter` (all exported by `cracked-up/inspect`), and written as the CSS variable `--level` on existing elements (brighter, thicker, and a moving dash while there is signal; modulators show their movement as a dotted line; the chip has a level bar). One animation-frame loop serves every row, taps exist only for rows on screen (IntersectionObserver), follow script rebuilds, and the loop stops when the context is not running, the page is hidden, or nothing is sounding. With reduced motion, levels are redrawn four times a second and nothing flows. (`services/chain-meters.ts`)

Added 2026-11-17; moved on 2026-11-17 from a footer tab to the track row, so a node's controls can be in the footer while its chain stays in view. The footer's tabs are **source, processors, sequence** ("processors" is the controls pane: every node's declared controls). The project bar has **one Seq / Signal toggle** ("Show steps" / "Show signal chains") that switches every track row at once: Seq (the default) shows each row's step grid and lane, Signal shows the chain in its place. It is one choice for all rows, remembered on the device (`rowsView` in the view's local storage) and not an undo step. The bar is three zones (`1fr auto 1fr`): the Sounds button and the toggle at the left, the transport centred, the layers button and New Track at the right; the project's name is not drawn in the bar (it stays as a visually hidden heading). On a phone the bar is two rows: the transport centred on the first, then Sounds, the toggle and the buttons. The Main Output row has no steps, so its buses are drawn in the row always, with no toggle.

- **It draws what the script made.** The picture is the running scope's graph, read through cracked-up's own inspector model (`cracked-up/inspect`: `readScope` and `buildModel`, which say which nodes carry audio or control signals, which are inserts of a bus, and where each bus goes), so it is complete and true even for a script Euclip cannot edit. The model's own layout and renderer are not used: a chain is a row, so the app arranges rows itself (`audio/chain-view.ts`). Each chain is a row of boxes (type, and the id if the script gave one) ending at a chip for where it goes: `channel` (the track's strip), another bus, the speakers. A node with two connections out gives a second row marked as a branch. A modulator is a row of its own, ending at the parameter it moves, with a dashed line labelled "modulates" (and a title such as `lfo → filter.frequency`). The main output shows each bus: its inserts in order, then where it goes. A row longer than the pane scrolls sideways inside it.
- **It edits by rewriting the script.** Tapping a node chooses it, chooses its track, and shows it in the footer at once (a source in the source tab with its editor chosen (a sampler's waveform, an oscillator's or synth macro's synth editor), any other node at its section of the processors tab (the footer's controls pane, renamed because source has controls too), outlined for a moment); there is no Open step. The **toolbar** is part of the selected track's row in Signal view (the Main Output's too, when it is the selected "track"), always there whether or not anything is chosen, in the same place with the same buttons, so choosing or clearing a choice moves nothing; unselected rows have none. Its actions are icons (named by `aria-label`; the name shows as a tooltip on hover and keyboard focus, and in words under the icon on touch screens): Add before, Add after, Insert node here, Move left, Move right, Remove, Add modulator, Add chain and one route slot. Actions that do not apply are disabled, not left out, and one sentence behind the toolbar's "?" says why; the chosen item's name is a fixed-width cell at the left. **Connections are selectable** (the arrow between two boxes, and into the end chip; the hit area is touch-sized): *Insert node here* adds between the two (the same edit as Add after the first); the route slot is *Send to…* for the link into the end (the chip's menu), *Branch to…* for a link between nodes or a chosen node (writes `__('#id').to('bus');`, a second statement using the library's selection `.to`, which adds a connection and removes none, so nothing after the node is lost; drawn as a branch), and *Retarget* with *Remove modulator* for a modulation link or a modulator's box. *Add chain* appends `__()\n  .<source>({ id })\n  .to('channel');` (`'main'` in the project script) with its `controls('#id');`, the source picked from the library's sources. Escape, or a tap on empty space in the chain, chooses nothing; the toolbar stays. Where a chain goes is a button: tapping it opens its Send to… list directly (choosing an item is the second tap, so nothing is sent by accident); tapping the dashed parameter box of a modulator opens the retarget list. On a long chain the destination is pinned at the right edge of the line. Each action is the script text a person would have typed, one undo step, run at once; if it does not build, the previous version keeps running and the error shows as it does for typed code, and the chain says it is drawing the running version. While the script has an error, editing from the chain is off. The footer's error and warning strip is shown only while the Script view is open; closed, a script error is a mark on the Script button (named "Script has an error"), so nothing shifts and a broken track is not silent.
- **How it finds the place** (`script-edit/`, pure functions from script text and an action to new text, or `{ cannot: reason }`). The script is parsed with acorn (a new direct dependency; it was already in `node_modules` for the linter), never searched with patterns. Edits are ranges of the original text, so every other character stays. Generated code always has an id (`.lowpass({ id: 'lowpass' })`, then `lowpass_2`: unique among the ids in the script and in the running graph), one node call to a line when the chain is written that way (a single-line chain gets a single-line call), and, for an added node or a modulator, `controls('#id');` at the end of the `// Controls` section (or of the script).
- **Recognised shapes.** A top-level `__()...;`, `const x = __()...;` or `__.bus('name')...;` whose calls are node calls (the library's node types), optionally ending in `.to('name')`, `.connect(...)` or `.modulate('#id', 'param')`; the modulator form is `__().lfo({ id: 'lfo', ... }).modulate('#filter', 'frequency');`. A node drawn is matched to a call by its `id` literal (which must be written once in the script), or, with no id, by type and creation order, which is accepted only when no other code in the script could make nodes and the drawn count of that type equals the script's.
- **Refused, with the reason beside the disabled action:** a syntax error; loops, functions, conditionals and `.split()` (the node shows "edit in script"); nodes made by those; an id that is computed, or written twice; an un-id'd node when other code may make nodes; a chain ending in `.connect(...)` (it has no bus to change); a bus with no `.to(...)` of its own; nothing is added before a chain's source or moved past it; on a bus `gain` and `input` are the bus's own, not inserts.
- **Remove** also deletes the control declarations (`slider`, `knob`, `toggle`, `select`, `controls`, `waveform`, `synth`) whose first argument is exactly `'#id'`, and any modulator statement that moves the node. Stored control values stay in the document, so undo restores everything. Removing a chain's source, or its only node, removes the whole statement, after a confirmation that says so.
- **Destinations.** Send to… rewrites the chain's `.to('…')` (or appends one) and lists the track's `channel`, `main` and the buses of the project and the script. The library does **not** make a bus because something is sent to it: `.to('name')` fails with a `missing-target` error if no bus of that name is in scope (only `__.bus('name')` makes one). So "New bus…" writes `__.bus('name');` into the **project script** (a bus there is visible to every track; in a track's script it would be that track's alone), then `.to('name')` into the track, as one undo step.
- **Modulators.** "Add modulator" offers the node's number parameters the library marks `rate: 'audio'`, which its documentation names as the valid modulation targets (so a sampler offers `gain`, not `speed`; macros are left to the script), and the library's modulator types (`lfo`, `stepper`). The depth is a quarter of the range, or half the current value for a logarithmic parameter. A target with no id is given one in the same edit.
- **Branches (2026-11-20).** A branch is `__('#id').to('bus');`, or, once it has nodes of its own, `__('#id')\n  .chain()\n  .<type>({ id })\n  .to('bus');`. Nodes of a branch go through the selection's `.chain()` (documented: a chain whose first new node is fed by every selected node); a node call straight on a selection (`__('#id').delay(...)`) only *sets* parameters and makes nothing, so it is never written. Checked with a real engine: the node is made once, fed from the start node and sent on, a rebuild of the same text keeps the same nodes, and the main chain is untouched. The analyser recognises exactly that shape (a `#id` selector, an optional `.chain()` followed by node calls, a final `.to('x')`); other selection statements are still refused. **Identity is a place, not an id:** a branch row (`ChainRow.shared` leading nodes, `twin` among identical bare branches) draws the node it starts from again, dashed and marked "main chain", and a choice is `(row, index)`, so the same node in two rows is two different things. The branch's start is the main chain's: Add before, Move and Remove are off with that reason; Add after (and Insert on the branch's links) writes into the branch's own statement (`findBranch`), as do Move, Remove, Send to… on the chip, and Insert on a node the branch made. Selecting the start (or the one link of a branch that makes nothing) offers **Remove branch** (confirm; the statement, the controls of nodes only it made, and what hangs on those nodes). **Removing a main node that a branch starts from removes the branch too** (as it does for its modulators), and the confirm says so. Add modulator and Branch to… work by node id and so are the same everywhere.

### Source and processors; the synth source editor

Added 2026-11-19. The footer's second tab, "processors", and the first, "source", both hold declared controls; **the node decides which**.

- **What a source is.** A node whose type the library puts in the category `source` (sampler, the four oscillators, noise), or a synth macro (a macro whose category is `synth`: `monosynth`, `polysynth`). Modulators (lfo, stepper), envelopes, filters and the rest are not sources. A control declared for a source node (by `slider`, `knob`, `toggle`, `select` or `controls()`) is listed in the source tab, with that source's editor, and **never also under processors**; every other control stays in processors. (One control over several nodes is a source's only if it is over one node.) The library has no public flag for "a macro with no audio input", so a user macro of another category is not told apart from an effect and stays under processors (`ProjectRunner#isSource`).
- **The sampler's controls** are below its waveform editor in the source tab, minus what the editor already shows (start, end, loop points, loop, reverse, speed), so `slider('#sampler', 'speed')` no longer has a row in processors.
- **`synth(target, options?)`** declares the editor of an oscillator or synth macro, as `waveform(target)` does for a sampler. Options: `label`, and `pitch` (the parameter the keyboard sets; default `frequency`, else the first parameter in Hz). It is a view over the node's other declared controls and over the pitch: if the script declares no control for the pitch, `synth()` makes one (hidden, with the key a `slider(target, pitch)` would have, `#osc › frequency`), so the stored value is the same one a note-mode slider holds, in Hz. A `slider` for the pitch in the script is that control, and is also listed as a row. `controls()` with no argument declares a `synth()` for every source that is not a sampler; an explicit `synth()` wins. On a sampler, or on a node that is not a source, it is a warning on its line. A synth macro is pitched by the note it is triggered with, not by a parameter, so its keyboard plays notes and keeps no pitch.
- **The editor** is laid out on fixed grid tracks (no scrolling at laptop sizes): above 57rem of room, two columns, with the octave row and the keyboard in the main column and a small scope with the compact control rows under it at the side; from 37rem, the scope at the right of the title and octave row, the keyboard full width, the controls in two columns; narrower (a phone), one column. It has an oscilloscope, a keyboard, then the controls as the app's standard rows; **no step strip** (2026-11-22: steps are on or off, and the melody is the pitch's lane, shown by the lane switch at the start of the octave row in the keyboard's place, its bars filling the keyboard's height). The scope draws the node's own output in cyan on the dark surface, triggered on a rising zero crossing, a flat line for silence, scaled to fill the height; it listens with `cracked-up/inspect`'s `TapSet` (an analyser off the output, never in the signal path; the library exports no scope drawing, so the trace is drawn on a canvas by `services/source-scope.ts`), in one animation-frame loop that runs only while a scope is on screen, the context is running and the page is shown, and rests after a second of silence; reduced motion redraws four times a second. The keyboard is two octaves (one at narrow widths) with octave buttons. **The shown octave range changes only with the − and + buttons (or PageDown and PageUp on the keyboard)**: it is set once when the editor first shows, to where the pitch is, and setting a pitch never moves it. A press sets the pitch control's single value (one undo step; a drag across keys glides through notes as one step), marks the key of the nearest note and shows the cents, and plays the note. It is one focusable control: arrows move a semitone (a step each), Enter and Space play. Steps with a pitch of their own in the lane keep it: the keys set the others, and the editor says so.
- **Noise** has no editor: a static "noise" picture (fixed bars in the app's colours, nothing drawn per frame, no scope tap, no keyboard, no steps) with its name in the tab list. `controls()` declares no controls for a noise node (its one parameter, `gain`, only appears if the script asks: `slider('#hiss', 'gain')`); `synth('#hiss')` gives the same picture with no warning.
- **Auditioning** (`ProjectRunner#playNote`): a synth macro is triggered with the note as its `pitch`; an oscillator has its pitch parameter set and the oscillator and every triggerable node after it (an envelope) triggered, and on release the same are released, except an oscillator with an open gate or an envelope after it, so a key never closes a gate the script left open. It works whether or not the transport plays.
- **The signal chain** opens the source tab on the editor of a source (waveform or synth); any other node opens processors.
- **New Track > Synth**: a `monosynth` to `channel`, a 16-step sequence whose callback is `if (ev.value) __('#synth').trigger({ duration: 0.12 })`, the grid, `synth('#synth')` and sliders for the macro's cutoff, resonance, attack, release and level. **A step that is on plays the synth's pitch on that step** (2026-11-22): the monosynth has a `frequency` parameter in cracked-up, the note a trigger with no `pitch` plays; `synth()` makes its control ("pitch", in notes, C1 to C7) and the keyboard sets it; the template's bass figure in C minor is the pattern (on/off) plus the pitch lane (the keyboard's C2, with G2, D#2 and F2 on their steps). The macro is gated: its envelope is closed until triggered, so its output, and the scope on it, are silent between notes. Saved projects with the older template (notes as step values) are unchanged: their scripts still pass `ev.value` as the pitch.
